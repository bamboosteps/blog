如果你已经会写 Hello World 内核模块、知道 `platform_driver` 和设备树是什么,但还没接触过 GPIO 子系统,这篇文章正适合你。如果你完全没写过内核模块,建议先补一下"字符设备驱动 + 设备树基础"再回来看这篇。

## 1. 先从硬件角度理解 GPIO

GPIO 全称 **General Purpose Input/Output**(通用输入输出引脚)。一颗 SoC(比如 ARM 芯片)上有成百上千个引脚,除了少数专用引脚(电源、晶振、DDR 总线等),大部分引脚都可以配置成 GPIO,由软件决定它是:

- **输入**:读取外部电平(比如读一个按键有没有被按下);
- **输出**:软件设置高低电平(比如点亮/熄灭一个 LED)。

从硬件寄存器的角度看,一个 GPIO 控制器通常至少包含这几组寄存器(不同厂商命名不同,原理类似):

- **方向寄存器**:每一位对应一个引脚,决定这个引脚是输入还是输出;
- **数据寄存器**:读的时候返回引脚当前电平,写的时候设置输出电平;
- 有的控制器还有**中断使能寄存器**、**上下拉配置寄存器**等。

Linux 内核要做的事情,就是把这些"厂商各不相同的寄存器操作"统一抽象成一套**标准接口**,让上层驱动(比如 LED 驱动、按键驱动)不需要关心底层到底是哪颗 SoC 的 GPIO 控制器。这套抽象层就是 **gpiolib**。

## 2. Linux GPIO 子系统总览(以 4.9 为准)

### 2.1 gpiolib:核心抽象层

gpiolib 的核心代码在 `drivers/gpio/gpiolib.c`,对应的头文件主要有两个,分别面向两种完全不同的"角色":

| 头文件 | 面向角色 | 说明 |
|---|---|---|
| `include/linux/gpio/driver.h` | **Provider(提供者)** | 写 GPIO 控制器驱动的人用,核心是 `struct gpio_chip` |
| `include/linux/gpio/consumer.h` | **Consumer(使用者)** | 写"用到某个 GPIO"的驱动的人用,核心是 `gpiod_*` 系列函数 |

这是理解整个 GPIO 子系统最关键的一条线索:**永远要分清楚自己现在是在写 Provider 还是 Consumer**。

- Provider:比如 SoC 内置 GPIO 控制器驱动、外挂的 I2C/SPI GPIO 扩展芯片(如 PCF8574、MCP23017)驱动。这类驱动**注册**一个 `gpio_chip`,告诉内核"我这里有 N 个 GPIO 引脚,读写方法分别是这些函数"。
- Consumer:比如 LED 驱动、按键驱动、某个传感器驱动里用一根 GPIO 做片选。这类驱动**不关心**这个 GPIO 具体来自哪个控制器,只管调用 `gpiod_get()` 拿到一个"描述符"(descriptor),然后用统一的 `gpiod_set_value()` / `gpiod_get_value()` 操作它。

### 2.2 新老两套 API

Linux GPIO 子系统在历史上出现过两套 consumer 侧 API:

1. **老的整数式 API**(`include/linux/gpio.h`):用一个全局唯一的整数编号代表一个 GPIO,比如 `gpio_request(45, "my-led")`、`gpio_set_value(45, 1)`。这套 API 从 Linux 早期就存在,问题是编号是"全局分配"的,同一个设备树在不同板子上跑,同一个引脚的编号可能都不一样,写出来的驱动很难跨平台复用。
2. **新的描述符式 API**(`include/linux/gpio/consumer.h`,从 Linux 3.13 开始引入,到 4.9 时已经是主流推荐做法):不再直接操作整数编号,而是通过 `gpiod_get(dev, "led", GPIOD_OUT_LOW)` 这样的函数,**根据设备树里的属性名**去拿到一个不透明的 `struct gpio_desc *` 指针,内核内部自己去做编号到具体引脚的映射。

**结论:在 4.9 内核上写新驱动,只要不是维护历史遗留代码,一律使用 `gpiod_*` 描述符 API**,本文后面的示例也只讲这一套。

### 2.3 用户空间怎么访问 GPIO

除了内核驱动之间互相调用,GPIO 也可以直接暴露给用户空间程序控制,4.9 内核上有三种方式:

1. **`/sys/class/gpio`(sysfs 接口,遗留)**:通过 `echo 45 > /sys/class/gpio/export` 导出一个 GPIO,再读写 `/sys/class/gpio/gpio45/value`。这是最早期、网上教程最常见的方式,但内核社区在很早就已经将它标记为 **deprecated**(不推荐新代码使用),原因是编号不稳定、缺乏原子性、无法很好地表达一次操作多个引脚等问题。
2. **`/dev/gpiochipN`(字符设备接口)**:Linux 4.8 才合入内核的新 ABI(`CONFIG_GPIO_CDEV`),4.9 已经自带。配合用户空间的 `libgpiod` 工具(`gpioinfo`、`gpioget`、`gpioset`、`gpiomon`)使用,是目前官方推荐的用户空间访问方式。
3. **debugfs 只读查看**:`/sys/kernel/debug/gpio`,纯粹用来看当前系统里注册了哪些 `gpio_chip`、每个引脚的方向和状态,方便调试,不能用来控制。

这一点对新手很重要:**如果你在网上搜到的教程还在用 `/sys/class/gpio/export`,要知道这是历史遗留方式,4.9 内核已经有更好的替代方案**,但作为了解调试手段之一,后面我们还是会简单介绍。

## 3. 核心数据结构

### 3.1 `struct gpio_chip`(Provider 侧)

这是 Provider 驱动要填写并注册给内核的结构体,定义在 `include/linux/gpio/driver.h`。挑几个最核心、写驱动时一定会用到的字段列出来:

| 字段 | 类型 | 作用 |
|---|---|---|
| `label` | `const char *` | 这个 GPIO 控制器的名字,会显示在 debugfs 里 |
| `parent` | `struct device *` | 指向对应的物理设备(比如 `platform_device` 的 `dev`) |
| `owner` | `struct module *` | 一般填 `THIS_MODULE` |
| `base` | `int` | 这个控制器起始的全局 GPIO 编号,填 `-1` 表示让内核自动分配,**强烈推荐填 -1** |
| `ngpio` | `u16` | 这个控制器一共管理多少根 GPIO |
| `get_direction` | 函数指针 | 查询某个引脚当前是输入还是输出 |
| `direction_input` | 函数指针 | 把某个引脚设置为输入 |
| `direction_output` | 函数指针 | 把某个引脚设置为输出,并给定初始电平 |
| `get` | 函数指针 | 读取某个引脚当前电平 |
| `set` | 函数指针 | 设置某个引脚的输出电平 |
| `can_sleep` | `bool` | 这个控制器的读写操作会不会睡眠(比如挂在 I2C/SPI 总线后面的扩展芯片就是 `true`) |
| `of_node` | `struct device_node *` | 对应的设备树节点,一般直接填 `dev->of_node` |

看到这张表你会发现,**写一个最简单的 Provider 驱动,本质上就是实现这 5 个回调函数(`get_direction`、`direction_input`、`direction_output`、`get`、`set`),然后调用一个注册函数**。这就是下一节要做的事。

### 3.2 `struct gpio_desc`(Consumer 侧)

Consumer 驱动完全不需要,也不应该关心 `struct gpio_desc` 内部长什么样——它是 gpiolib 内部维护的结构,消费者拿到的永远是一个**不透明指针** `struct gpio_desc *`,只能传给 `gpiod_*` 系列函数使用,不能直接访问里面的字段。这是内核里典型的"句柄(handle)"设计模式。

## 4. 设备树基础:一个 GPIO 控制器节点长什么样

假设我们要给一颗假想的 SoC 编写 GPIO 驱动,它的 GPIO 控制器占用一段 8 字节的寄存器空间,映射在物理地址 `0x10000000`,设备树节点大致是这样:

```dts
simple_gpio: gpio@10000000 {
    compatible = "example,simple-gpio";
    reg = <0x10000000 0x8>;
    gpio-controller;
    #gpio-cells = <2>;
};
```

几个关键属性:

- `gpio-controller`:一个空属性,告诉内核"这个节点是一个 GPIO 控制器",没有它,消费者节点里引用这个 phandle 时内核不会当作 GPIO 处理。
- `#gpio-cells`:告诉内核,消费者节点引用这个控制器的某个引脚时,需要几个参数。业界惯例是 `2`:第一个参数是引脚编号(在这个控制器内部的偏移,从 0 开始),第二个参数是极性标志(`GPIO_ACTIVE_HIGH` 或 `GPIO_ACTIVE_LOW`,定义在 `include/dt-bindings/gpio/gpio.h`)。

## 5. 动手写一个最小的 GPIO Provider 驱动

下面这份代码是一个**教学用途**的最小示例,针对上一节那个假想的内存映射 GPIO 控制器,一共管理 8 根引脚。真实芯片的寄存器布局要以厂商手册为准,这里只是让你看清楚 gpiolib 的调用骨架。

```c
// drivers/gpio/gpio-simple-demo.c
#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/of.h>
#include <linux/io.h>
#include <linux/gpio/driver.h>
#include <linux/spinlock.h>
#include <linux/slab.h>

#define REG_DATA   0x00   /* 数据寄存器:每 bit 对应一个引脚的电平 */
#define REG_DIR    0x04   /* 方向寄存器:对应 bit 为 1 表示这根引脚是输出 */

struct simple_gpio {
    struct gpio_chip chip;
    void __iomem *base;
    spinlock_t lock;
};

static inline struct simple_gpio *to_simple_gpio(struct gpio_chip *gc)
{
    return container_of(gc, struct simple_gpio, chip);
}

/* 查询某个引脚是输入还是输出:内核约定返回 0 表示输出,1 表示输入 */
static int simple_gpio_get_direction(struct gpio_chip *gc, unsigned offset)
{
    struct simple_gpio *sg = to_simple_gpio(gc);
    u32 dir = readl(sg->base + REG_DIR);

    return !(dir & BIT(offset));
}

static int simple_gpio_direction_input(struct gpio_chip *gc, unsigned offset)
{
    struct simple_gpio *sg = to_simple_gpio(gc);
    unsigned long flags;
    u32 val;

    spin_lock_irqsave(&sg->lock, flags);
    val = readl(sg->base + REG_DIR);
    val &= ~BIT(offset);
    writel(val, sg->base + REG_DIR);
    spin_unlock_irqrestore(&sg->lock, flags);

    return 0;
}

static int simple_gpio_direction_output(struct gpio_chip *gc, unsigned offset, int value)
{
    struct simple_gpio *sg = to_simple_gpio(gc);
    unsigned long flags;
    u32 val;

    spin_lock_irqsave(&sg->lock, flags);

    /* 先把输出电平设置好,再切换方向,避免切到输出瞬间出现毛刺 */
    val = readl(sg->base + REG_DATA);
    if (value)
        val |= BIT(offset);
    else
        val &= ~BIT(offset);
    writel(val, sg->base + REG_DATA);

    val = readl(sg->base + REG_DIR);
    val |= BIT(offset);
    writel(val, sg->base + REG_DIR);

    spin_unlock_irqrestore(&sg->lock, flags);

    return 0;
}

static int simple_gpio_get(struct gpio_chip *gc, unsigned offset)
{
    struct simple_gpio *sg = to_simple_gpio(gc);

    return !!(readl(sg->base + REG_DATA) & BIT(offset));
}

static void simple_gpio_set(struct gpio_chip *gc, unsigned offset, int value)
{
    struct simple_gpio *sg = to_simple_gpio(gc);
    unsigned long flags;
    u32 val;

    spin_lock_irqsave(&sg->lock, flags);
    val = readl(sg->base + REG_DATA);
    if (value)
        val |= BIT(offset);
    else
        val &= ~BIT(offset);
    writel(val, sg->base + REG_DATA);
    spin_unlock_irqrestore(&sg->lock, flags);
}

static const struct of_device_id simple_gpio_of_match[] = {
    { .compatible = "example,simple-gpio" },
    { }
};
MODULE_DEVICE_TABLE(of, simple_gpio_of_match);

static int simple_gpio_probe(struct platform_device *pdev)
{
    struct device *dev = &pdev->dev;
    struct simple_gpio *sg;
    struct resource *res;

    sg = devm_kzalloc(dev, sizeof(*sg), GFP_KERNEL);
    if (!sg)
        return -ENOMEM;

    res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
    sg->base = devm_ioremap_resource(dev, res);
    if (IS_ERR(sg->base))
        return PTR_ERR(sg->base);

    spin_lock_init(&sg->lock);

    sg->chip.label = "simple-gpio";
    sg->chip.parent = dev;
    sg->chip.owner = THIS_MODULE;
    sg->chip.base = -1;                 /* 让内核自动分配起始编号 */
    sg->chip.ngpio = 8;                 /* 这个假想控制器只有 8 根引脚 */
    sg->chip.get_direction = simple_gpio_get_direction;
    sg->chip.direction_input = simple_gpio_direction_input;
    sg->chip.direction_output = simple_gpio_direction_output;
    sg->chip.get = simple_gpio_get;
    sg->chip.set = simple_gpio_set;
    sg->chip.of_node = dev->of_node;
    sg->chip.can_sleep = false;         /* 直接寄存器读写,不会睡眠 */

    platform_set_drvdata(pdev, sg);

    /* devm_ 版本会在 probe 失败或设备卸载时自动调用 gpiochip_remove */
    return devm_gpiochip_add_data(dev, &sg->chip, sg);
}

static struct platform_driver simple_gpio_driver = {
    .driver = {
        .name = "simple-gpio",
        .of_match_table = simple_gpio_of_match,
    },
    .probe = simple_gpio_probe,
};
module_platform_driver(simple_gpio_driver);

MODULE_LICENSE("GPL v2");
MODULE_DESCRIPTION("A minimal example GPIO controller driver for teaching purposes");
```

逐段拆解一下这份代码在做什么:

1. **`devm_ioremap_resource`**:把设备树 `reg` 属性描述的物理地址映射成内核可以直接读写的虚拟地址,存在 `sg->base` 里。所有的 `readl()`/`writel()` 都是在操作这段映射后的地址。
2. **填 `gpio_chip` 的 5 个回调**:这是整个 Provider 驱动的核心,内核后续所有 `gpiod_*` 调用最终都会落到这几个函数上。
3. **`sg->chip.base = -1`**:表示不指定固定编号,交给内核统一分配,避免和系统里其他 GPIO 控制器编号冲突,这是官方推荐做法。
4. **`devm_gpiochip_add_data(dev, &sg->chip, sg)`**:真正把这个 `gpio_chip` 注册进 gpiolib。第三个参数 `sg` 是"私有数据",之后可以用 `gpiochip_get_data(gc)` 拿回来,不过我们这里因为用了 `container_of` 就没再用到它。用 `devm_` 前缀的版本意味着设备卸载(或 probe 失败退出)时,内核会自动帮你调用对应的清理函数,不需要手写 `remove()`。

## 6. 动手写一个 Consumer 驱动:用它点一个 LED

有了上面的 GPIO 控制器,我们再写一个"消费者"驱动,通过设备树引用第 3 号引脚,把它当作一个 LED 来驱动。

设备树里新增一个节点,引用刚才的 `simple_gpio`:

```dts
led0: led {
    compatible = "example,simple-led";
    led-gpios = <&simple_gpio 3 GPIO_ACTIVE_HIGH>;
};
```

注意属性名是 `led-gpios`,这不是随便起的——`gpiod_get()` 的第二个参数 `con_id` 会被内核自动拼接上 `-gpios` 后缀去设备树里找属性,这是一条**约定优于配置**的规则,新手很容易在这里踩坑(属性名写错,`gpiod_get` 就会返回 `-ENOENT`)。

对应的 Consumer 驱动代码:

```c
// drivers/misc/simple-led.c
#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/gpio/consumer.h>
#include <linux/of.h>
#include <linux/slab.h>

struct simple_led {
    struct gpio_desc *gpiod;
};

static const struct of_device_id simple_led_of_match[] = {
    { .compatible = "example,simple-led" },
    { }
};
MODULE_DEVICE_TABLE(of, simple_led_of_match);

static int simple_led_probe(struct platform_device *pdev)
{
    struct simple_led *led;

    led = devm_kzalloc(&pdev->dev, sizeof(*led), GFP_KERNEL);
    if (!led)
        return -ENOMEM;

    /* 对应设备树里的 "led-gpios" 属性,初始状态设为输出低电平 */
    led->gpiod = devm_gpiod_get(&pdev->dev, "led", GPIOD_OUT_LOW);
    if (IS_ERR(led->gpiod))
        return PTR_ERR(led->gpiod);

    /* 点亮 LED */
    gpiod_set_value_cansleep(led->gpiod, 1);

    platform_set_drvdata(pdev, led);
    return 0;
}

static int simple_led_remove(struct platform_device *pdev)
{
    struct simple_led *led = platform_get_drvdata(pdev);

    gpiod_set_value_cansleep(led->gpiod, 0);
    return 0;
}

static struct platform_driver simple_led_driver = {
    .driver = {
        .name = "simple-led",
        .of_match_table = simple_led_of_match,
    },
    .probe = simple_led_probe,
    .remove = simple_led_remove,
};
module_platform_driver(simple_led_driver);

MODULE_LICENSE("GPL v2");
MODULE_DESCRIPTION("A minimal example GPIO consumer driver for teaching purposes");
```

几个值得停下来解释的细节:

- **`devm_gpiod_get(dev, "led", GPIOD_OUT_LOW)`**:一步到位完成"请求 GPIO + 设置为输出 + 设置初始电平为低"。`GPIOD_OUT_LOW`/`GPIOD_OUT_HIGH`/`GPIOD_IN` 是 `enum gpiod_flags` 里定义的常用值,比自己再手动调 `gpiod_direction_output()` 省一步。
- **`gpiod_set_value_cansleep()` vs `gpiod_set_value()`**:这是新手最容易忽略的一个坑。如果这根 GPIO 来自一个可能睡眠的控制器(比如挂在 I2C/SPI 总线后面的扩展芯片,对应 `gpio_chip.can_sleep = true`),就必须用带 `_cansleep` 后缀的版本,否则在不允许睡眠的上下文(比如中断处理函数里)调用普通版本,内核会直接 `BUG_ON` 报错甚至死机。如果你不确定这根 GPIO 来自哪种控制器,统一用 `_cansleep` 版本更安全(前提是调用处本身允许睡眠,比如 `probe()` 函数里)。
- **`GPIO_ACTIVE_HIGH`**:设备树里这个标志会被 gpiolib 自动处理成"极性反转"。也就是说,即使硬件上这个 LED 是低电平点亮(`GPIO_ACTIVE_LOW`),Consumer 驱动代码完全不用改,调用 `gpiod_set_value(gpiod, 1)` 永远表示"逻辑上点亮",gpiolib 会自动帮你把 1 转换成硬件需要的实际电平。这也是为什么 4.9 时代强烈推荐用 `gpiod_*` API 而不是老的整数 API——极性这种细节,老 API 需要驱动自己处理。

## 7. 编译与加载

在你的驱动源码目录放一个最简单的 `Kbuild`(或 `Makefile`):

```makefile
obj-m += gpio-simple-demo.o
obj-m += simple-led.o
```

在内核源码树外单独编译成 `.ko` 模块(假设内核源码在 `/path/to/linux-4.9`):

```bash
make -C /path/to/linux-4.9 M=$(pwd) modules
```

如果是把驱动合入内核源码树一起编译,记得在对应的 `Kconfig` 里加一项开关,并确认 `menuconfig` 里以下选项已经打开(4.9 默认配置一般都开着,自己精简过内核配置的话要注意检查):

- `CONFIG_GPIOLIB`:GPIO 子系统总开关
- `CONFIG_OF_GPIO`:GPIO 的设备树支持
- `CONFIG_GPIO_SYSFS`:老的 sysfs 用户空间接口(可选)
- `CONFIG_GPIO_CDEV`:新的字符设备用户空间接口(推荐打开)
- `CONFIG_DEBUG_FS`:调试用的 debugfs(推荐打开,方便下一节调试)

加载模块并查看内核日志:

```bash
insmod gpio-simple-demo.ko
insmod simple-led.ko
dmesg | tail
```

如果 probe 成功,`dmesg` 里通常会看到 gpiolib 打印类似 `gpiochip_add_data: registered GPIOs xxx to xxx on device: simple-gpio` 的信息(具体格式因内核版本略有差异)。

## 8. 调试手段

### 8.1 debugfs:看当前系统里都注册了哪些 GPIO 控制器

```bash
mount -t debugfs none /sys/kernel/debug   # 如果还没挂载
cat /sys/kernel/debug/gpio
```

输出大致长这样:

```
gpiochip0: GPIOs 0-7, simple-gpio:
 gpio-3   (led0               ) out hi
```

这行信息完整地告诉你:第 3 号引脚已经被名叫 `led0` 的消费者请求,当前方向是输出、电平是高。**这是排查"GPIO 到底有没有被正确请求、方向和电平对不对"最快的手段**,新手调试时应该第一时间想到它。

### 8.2 遗留方式:sysfs

```bash
echo 3 > /sys/class/gpio/export      # 导出编号为 3 的 GPIO(编号要以 debugfs 里看到的全局编号为准)
cat /sys/class/gpio/gpio3/direction  # 查看方向
echo 1 > /sys/class/gpio/gpio3/value # 设置为高电平
echo 3 > /sys/class/gpio/unexport    # 用完记得 unexport
```

再强调一次:这套接口官方已标记为 deprecated,能用来临时验证硬件没问题,但**不要**在正式驱动代码或者长期维护的脚本里依赖它。

### 8.3 推荐方式:字符设备 + libgpiod 工具

4.9 内核已经支持 `/dev/gpiochipN` 字符设备接口,配合用户空间 `libgpiod` 提供的小工具使用体验更好(工具需要单独编译/安装,不是内核自带):

```bash
gpiodetect            # 列出系统里所有的 gpiochip
gpioinfo gpiochip0     # 查看这个 chip 下每根引脚的用途和状态
gpioget gpiochip0 3    # 读取 3 号引脚电平
gpioset gpiochip0 3=1  # 设置 3 号引脚为高电平
```

## 9. 新手常踩的坑

1. **忘记用 `devm_` 系列函数**:自己手写 `remove()` 里忘记调用 `gpiochip_remove()` 或 `gpiod_put()`,导致模块卸载后资源没释放,下次加载直接报错或者引用悬空指针。用 `devm_gpiochip_add_data()`、`devm_gpiod_get()` 基本可以规避这个问题。
2. **设备树属性名和 `con_id` 对不上**:`gpiod_get(dev, "led", ...)` 只会去找 `led-gpios`,如果设备树里写成了 `led0-gpios` 或者干脆漏写了 `-gpios` 后缀,`gpiod_get()` 会返回 `-ENOENT`,报错信息也不会特别直白,新手容易卡在这里排查半天。
3. **`can_sleep` 判断错误导致的 `_cansleep` 混用**:总线型 GPIO 扩展芯片(I2C/SPI 后面的)一定要用 `_cansleep` 版本的读写函数,并且不能在中断上下文、自旋锁保护的代码里调用它们。
4. **`gpio_chip.base` 写死成固定值**:如果手写了一个固定的 `base` 编号,一旦系统里同时存在多个 GPIO 控制器,很容易和别的驱动分配到的编号段冲突。永远优先用 `-1` 交给内核自动分配。
5. **direction_output 里先切方向、后设置电平**:如果代码顺序反了,引脚在从输入切换到输出的瞬间会先输出上一次遗留的电平,可能出现短暂的毛刺,对有些外设(比如某些使能引脚)是致命的。本文示例里特意先写数据寄存器、再写方向寄存器,就是为了避免这个问题。

## 10. 小结

这篇文章按照"硬件是什么 → gpiolib 整体架构 → 核心数据结构 → Provider 驱动怎么写 → Consumer 驱动怎么写 → 怎么编译加载 → 怎么调试 → 常见坑"的顺序,完整过了一遍 Linux 4.9 内核 GPIO 子系统的核心用法。如果你能照着第 5、6 节的代码自己敲一遍、跑起来、再用 debugfs 验证一下引脚状态,基本就算入门了。

后面如果有兴趣深入,可以继续研究:

- GPIO 中断:`gpiochip_irqchip_add()`,如何让一个 GPIO 控制器同时支持产生中断(按键驱动会用到);
- 真实的厂商 GPIO 驱动,比如 `drivers/gpio/gpio-pl061.c`(ARM PrimeCell PL061)或 `drivers/gpio/gpio-74x164.c`(SPI 移位寄存器 GPIO 扩展),对照本文的最小示例,看看真实驱动多处理了哪些边界情况;
- 用户空间 `libgpiod` 的 C/C++ API,如何在不写内核驱动的情况下,直接从用户态操作 GPIO。
